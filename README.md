# Pac-Man

## Description

A remake of the 1980 Namco arcade classic, written in Python with
[pygame-ce](https://pyga.me/). Pac-Man runs through a maze eating pacgums
while four ghosts hunt him down. Eating a super-pacgum (power pellet) in a
corner turns the ghosts blue for a few seconds, and Pac-Man can eat them.

Every maze is generated by the **A-Maze-ing** package assigned to us by
another group. The first level always uses the seed from the config file, so
it is the same maze each time. The next levels use random seeds.

Features:

- 10 levels. A level is won when every pacgum is eaten, and the game is won
  after the last level.
- 3 lives (configurable) and a time limit per level.
- Four ghosts, each with its own behaviour, plus frightened, eaten (eyes going
  home) and blinking states.
- Animated Pac-Man (mouth chomping in the walking direction).
- Main menu, instructions, pause menu, victory and game over screens.
- Persistent top 10 highscores, with name entry at the end of a game.
- Cheat mode for the defense (see [Controls](#controls)).

## Instructions

### Requirements

- Python 3.10 or later
- [uv](https://docs.astral.sh/uv/)

### Installation and execution

```sh
make install                    # uv sync: creates .venv with all dependencies
make run                        # uv run python3 pac-man.py config/config.json
```

Or, inside the virtual environment:

```sh
python3 pac-man.py config/config.json
```

The only argument is the path of the config file, absolute or relative to the
folder the game is run from. It must be a `.json` file. The assets and the
highscore database are always found from the project folder, so the game can
be run from anywhere.

### Other Makefile rules

| Rule               | What it does                                               |
|--------------------|------------------------------------------------------------|
| `make debug`       | Run the game under `pdb`                                   |
| `make clean`       | Remove the caches and the `build/` and `dist/` folders     |
| `make lint`        | `flake8` and `mypy` with the flags required by the subject |
| `make lint-strict` | `flake8` and `mypy --strict`                               |
| `make test`        | `pytest`: broken files and permissions, every screen       |
| `make package`     | Build the packaged game in `dist/` (see Packaging)         |

The tests in `tests/` check that the game never crashes: missing files,
missing permissions, invalid JSON, broken assets, an unwritable or corrupted
database and extreme config values must end with a clear error or a warning.
They use a copy of the assets and a temporary database, so they never touch
`db/leaderboard.db`.

### Packaging

`make package` builds a standalone game with
[PyInstaller](https://pyinstaller.org), from the spec `pacman.spec` at the
root of the repository. Players don't need Python or any dependency.

```
dist/pacman/                 the game folder
├── pacman                   the executable (pacman.exe on Windows)
├── config.json              the config, edit it to change the game
├── README.txt               in-package instructions (packaging/README.txt)
├── db/leaderboard.db        the highscores, created at the first launch
└── _internal/               Python, pygame-ce, mazegenerator and the assets
dist/pacman-<platform>.zip   the same folder, zipped for itch.io
```

The packaged game differs from `python3 pac-man.py` in two ways
(`FROZEN` and `APP_DIR` in `src/definitions.py`):

- Started without an argument (double click, itch.io app), it uses the
  `config.json` next to the executable. Another config can still be given
  as the only argument.
- The highscores are saved next to the executable, in `db/`, because the
  assets folder is PyInstaller's internal folder.

PyInstaller doesn't cross-compile: the zip only runs on the system it was
built on (`pacman-linux.zip` on Linux, `pacman-darwin.zip` on macOS,
`pacman-win32.zip` on Windows). Build on the system of the players, then
upload the zip to the itch.io project page as a downloadable file for that
system, with the project visibility set to "Restricted" or "Draft" so it
stays private.

## Configuration

The config is a JSON object. Lines starting with `#` are treated as comments
and removed before parsing.

```json
{
  "level": [],
  "width": 14,
  "height": 14,
  "lives": 3,
  "pacgum": 42,
  "points_per_pacgum": 10,
  "point_per_superpacgum": 50,
  "points_per_ghost": 200,
  "seed": 42,
  "level_max_time": 120
}
```

| Key                     | Default | Meaning                                                        |
|-------------------------|---------|----------------------------------------------------------------|
| `level`                 | `[]`    | Size of each level, as `{"width": w, "height": h}` objects     |
| `width`                 | `14`    | Maze width in cells, for levels not listed in `level` (12–25)  |
| `height`                | `14`    | Maze height in cells, for levels not listed in `level` (12–15) |
| `lives`                 | `3`     | Lives at the start of the game                                 |
| `pacgum`                | `42`    | Validated, but not used: every open cell gets a pacgum         |
| `points_per_pacgum`     | `10`    | Points for a pacgum                                            |
| `point_per_superpacgum` | `50`    | Points for a super-pacgum                                      |
| `points_per_ghost`      | `200`   | Points for an edible ghost                                     |
| `seed`                  | `42`    | Seed of the first level's maze                                 |
| `level_max_time`        | `90`    | Seconds to clear a level. Running out of time ends the game    |

Error handling (`src/parser.py`):

- Every value except `level` must be a strictly positive integer.
- A missing or invalid value prints a warning on stderr and uses its default.
- Unknown keys are ignored, with a warning.
- `width` and `height` are clamped to the limits above, so the menus fit and
  the window fits on a screen. The same check and clamping applies to each
  `level` entry, and a missing or invalid size in an entry falls back to the
  global `width` / `height`.
- An unreadable file, a file that is not valid JSON or a JSON value that is
  not an object stops the program with a clear `Error:` message, never a
  traceback.

## Highscore

Highscores are stored in a SQLite database, `db/leaderboard.db`, with one
`highscore(name, score)` table (`src/database.py`).

- At the end of a game (win or lose), the player types a name. Names have at
  most 10 characters and accept letters, digits and spaces only. They are
  saved in uppercase. An invalid name shows the reason on screen and is not
  saved.
- Each name keeps only its best score. A new name is inserted, and a known
  name is updated only if the new score is higher.
- The leaderboard in the main menu shows the top 10, highest score first.
- The `db/` folder and the table are created if missing. Any SQLite error
  (missing, locked or corrupted file) prints one warning and the game keeps
  running. Saving then does nothing, and the leaderboard is empty.

We chose SQLite because it ships with Python (no extra dependency). It also
handles the sorting and the top 10 limit in one query, and it is safer than
rewriting a whole JSON file at each save: a crash in the middle of a save
can't leave a half-written file.

## Maze Generation

The assigned package is installed as-is from its wheel
(`maze/mazegenerator-2.1.0-py3-none-any.whl`, declared in `pyproject.toml`).
`src/maze.py` wraps it:

```python
MazeGenerator(size=(width, height), seed=seed, perfect=False)
```

- `perfect=False` opens extra passages, so the maze has loops like a real
  Pac-Man board instead of dead ends only.
- The generator returns a grid of integers, one per cell. Each bit is a wall:
  `N = 1`, `E = 2`, `S = 4`, `W = 8`. A cell equal to `15` is closed on all
  sides: it is the "42" pattern drawn by the generator, shown in gray, and it
  holds no pacgum.
- `Maze` builds a neighbour graph from these bits, used by the ghosts'
  path finding. It also finds the open cell closest to a point: the center for
  Pac-Man's spawn, and the four corners for the ghosts and super-pacgums.
- Any exception from the generator stops the game with a clean error message.

## Implementation

- **Game loop** (`Render.display`): runs at 30 FPS. Each frame reads the
  events, updates the game with the elapsed time `dt` and draws the current
  screen. The screens (menu, playing, paused, instructions, leaderboard,
  victory, game over, save) are a `Screen` enum.
- **Movement**: Pac-Man and the ghosts move cell by cell. Each entity has a
  speed `vel` in cells per second: `tick(dt)` adds up time and allows one step
  every `1 / vel` seconds. The drawing interpolates between the previous and
  the current cell, so the movement looks smooth. Pac-Man remembers the last
  wanted direction and turns as soon as it is possible.
- **Collisions**: Pac-Man and a ghost collide when they are on the same cell,
  or when they swapped cells during the same step (crossing each other).
- **Ghosts**: all of them use a BFS over the maze graph.
  - Blinky follows the shortest path to Pac-Man.
  - Pinky aims at a cell 4 steps away from Pac-Man.
  - Clyde aims at a cell 8 steps away from Pac-Man.
  - Inky moves randomly: it goes straight and picks a random open
    direction when blocked.
- **Ghost states**: `CHASE`, `FRIGHTENED` and `EATEN`.
  - A super-pacgum makes the ghosts `FRIGHTENED` for 7 seconds. They run
    away from Pac-Man and blink white during the last 2 seconds.
  - An eaten ghost becomes a pair of eyes that goes back to its corner,
    waits there for a moment, then goes back to `CHASE`.
- **Levels**: a level ends when all pacgums and super-pacgums are eaten. The
  next one gets a new random maze, with the size from `level` (or the global
  size). The window is resized when the maze size changes.
- **MLX compatibility**: the subject only allows functions that have an
  equivalent in the MLX. The game only creates a window, loads images,
  copies images and pixels, and reads key events: walls, pacgums and text are
  PNG images, and the text uses a bitmap font made from `pacman.ttf`. See
  [MLX_COMPATIBILITY.md](MLX_COMPATIBILITY.md).

## General Software Architecture

```
pac-man.py            entry point: calls src.__main__.main
src/
  __main__.py         argument check, builds Config, Game, Draw and Render
  parser.py           Parser: reads and validates the JSON config
  config.py           Config: dataclass with the validated values
  definitions.py      constants, colors, directions, Screen/GameState/GhostState
  maze.py             Maze: wraps the A-Maze-ing generator, neighbour graph
  entity.py           Entity: position, speed, tick, wall checks
  pacman.py           Pacman(Entity)
  ghosts.py           Ghost(Entity) and Blinky, Pinky, Inky, Clyde(Ghost)
  game.py             Game: levels, score, lives, collisions, cheats
  database.py         Database: SQLite highscores
  draw.py             Draw: loads the assets and draws every screen
  font.py             BitmapFont: draws text from the baked font images
  render.py           Render: main loop, input handling, screen changes
assets/               sprites (game, hud, menu) and the font
config/config.json    default configuration
db/leaderboard.db     highscores (created at run time)
```

How the classes fit together:

- `Parser` produces a `Config`, which `Game` receives.
- `Game` owns the `Maze`, the `Pacman`, the four ghosts and the `Database`.
  It holds all the rules and knows nothing about drawing or input.
- `Draw` reads the `Game` state and only draws it.
- `Render` holds the `Game` and the `Draw`. It turns key presses into calls
  to `Game` and picks the screen to draw.
